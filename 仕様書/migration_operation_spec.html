🚚 ⑤ 3.17TB 無停止データ移行・本番切替・障害復旧（BCP）仕様書

稼働中の旧 RS-Base サーバ（192.168.1.164：検査 193,822件・患者 179,659名・実データ 3.17TB）に一切の負荷や変更を加えず、通常診療を続けながら新サーバへ段階コンバートし、休診時間のわずか15〜30分で安全に 192.168.1.164 を引き継ぐ手順および導入後のBCP（事業継続）手順を定義します。

🔄1. コンバートエンジン migration/migrate_from_rsbase.py 仕様
レジューム・差分同期対応
⛔ 最重要安全原則：旧サーバ（192.168.1.164）に対する完全 Read-Only アクセス
マイグレータは旧 gazouDB に対して SELECT クエリのみを発行し、共有フォルダ（\\192.168.1.164\D\Users\rsn\public_html）からも読み取りコピーのみを行います。旧サーバ側のファイルを移動・書換・削除することは一切ないため、万一切替当日に想定外の事象が起きても旧サーバで即座に100%通常診療を継続できます。
変換項目 コンバート変換ルール詳細
患者マスタ変換
name_tbl ➔ patients		 全179,659件の SHIFT_JIS (CP932) 文字列（外字・旧字体・半角カナ含む）をUTF-8へ無欠損変換。kanja_yomi_norm（全角カタカナ正規化列）を自動生成し、和暦/西暦混在の生年月日を DATE 型へパースして UPSERT します。
年度別マルチSSD自動振分
archive_cutoff_year: 2021		 ・検査年 2000〜2021年 ➔ VOL_ARCHIVE（本番 D: 4TB SSD #1 / 約2.2TB）へ配置
・検査年 2022年〜現在 ➔ VOL_ACTIVE（本番 E: 4TB SSD #2 / 約1.0TB）へ配置
これにより移行完了時点で E: ドライブに約3.0TB（今後8〜10年分）の空き容量が確保されます。
旧連番・所見の完全継承
gazou_tbl ➔ studies		 旧 gazou_tbl.renban を studies.legacy_renban（UNIQUE）に保持。すでに同一 legacy_renban が移行済みの場合は高速スキップするため、何度中断・再実行しても重複せず差分のみ追記できます。sindan1〜sindan4・txt1RS/kensa.txt 内の所見も統合して findings と study_meta.json に保存します。
実ファイルクリーン格納
Imfidx* / ecg/*		 旧検査フォルダ内の純粋な検査データ（*.dcm, *.jpg, *.ECG 等）のみを抽出し、不要な旧管理ゴミファイル（txt1RS, 000.shoken, 古い極小サムネイル）を除外したクリーンな連番構造＋新規高画質キャッシュへ再編成します。
放置未紐付けデータの救出
D:\CR\~NoNumber*.dcm		 現行 192.168.1.164 の D:\CR に2019〜2020年から放置されている26件のID未入力DICOMファイルも取りこぼさず新サーバの quarantine_queue へ保護回収し、Web画面上で確認・整理できるようにします。
📅2. 3フェーズ段階移行スケジュール（診療無停止）

Phase 1：事前一括バックグラウンド移行

実施タイミング: 通常診療日〜夜間（数日かけてOK）

Windows Server 2025 新サーバに仮IP（例: 192.168.1.165）を設定してLAN接続。ネットワーク帯域を圧迫しないようスループット制御付きで migrate_from_rsbase.py を実行し、過去26年分（3.17TB）の99.9%を事前コピー＆変換完了させます。

Phase 2：並行リハーサル・疎通検証

実施タイミング: 切替前の昼休み・診療後

診察室PCや管理者端末から仮IP（http://192.168.1.165/rsnext/）を実際に開き、過去画像の高速表示・12誘導心電図・2×4印刷・CD作成・JPEG出力を実データで確認。モダリティからのテスト送信（DICOM C-ECHO等）も事前チェックします。

Phase 3：差分同期 ＆ IP引き継ぎ切替

実施タイミング: 休診日または午後休診（所要 15〜30分）

Phase 1 以降に増えた直近数日分の検査・患者データ（数GB・数百件）のみを差分同期（約3〜5分）➔ 自動ベリファイ合格後、旧サーバを待機IPへ退避して新サーバへ 192.168.1.164 を付与し本稼働を開始します。

✅3. 本番カットオーバー当日 実行手順チェックリスト
  1. 当日検査の終了確認: 内視鏡・X線・エコー・心電計からの送信が完了していることを確認する。
  2. 最終差分マイグレーション実行: 新サーバで python migration/migrate_from_rsbase.py --delta --verify を実行し、gazou_tbl 最新 renban まで100%一致したことを確認する（約5分）。
  3. 初回ミラー同期確認: 新サーバの D:➔F: および E:➔G: の robocopy /MIR が最新状態であることを確認する。
  4. 旧サーバのIP退避（コールドスタンバイ化）: 旧サーバ（192.168.1.164）のIPを 192.168.1.169 等へ変更（またはLANケーブルを抜線してそのまま電源温存）する。
  5. 新サーバへの 192.168.1.164 設定: Windows Server 2025 新サーバのNICに 192.168.1.164 を設定し、ipconfig /flushdns および ARP 更新を確認する。
  6. 全チャネル着信ワンパス確認（約10分）:
    • MALL3 からテスト患者更新出力 ➔ DRS\kanja.txt 着信・即時DB反映確認
    • 内視鏡（FTP Port 21）、X線・エコー（DICOM Port 104）、心電計（TCP Port 1001）の疎通確認
    • 診察室ブラウザから一覧表示・カルテ連携・Webビューワ表示を確認して切替完了！
🛡️4. 日次自動ミラーリング ＆ 8TB HDD 世代バックアップ仕様

Windows タスクスケジューラに登録する標準保守ジョブにより、人手ゼロで3重のデータ保護を維持します。

# 1. 現役SSD (E:) ➔ ミラー待機SSD (G:) 高速同期（1時間ごと、または昼・夜1日2回）
robocopy "E:\rsnext_active" "G:\rsnext_active" /MIR /FFT /R:2 /W:3 /MT:16 /NP /LOG+:"C:\rsnext\logs\mirror_active.log"

# 2. アーカイブSSD (D:) ➔ ミラー待機SSD (F:) 同期（週1回または更新時）
robocopy "D:\rsnext_archive" "F:\rsnext_archive" /MIR /FFT /R:2 /W:3 /MT:16 /NP /LOG+:"C:\rsnext\logs\mirror_archive.log"

# 3. 毎晩 23:00 PostgreSQL 18 完全圧縮ダンプ ＋ 8TB HDD (H:) への退避（30日世代保持）
pg_dump -U postgres -Fc rsnext_db -f "H:\rsnext_backup\db_dumps\rsnext_db_%DATE:~0,4%%DATE:~5,2%%DATE:~8,2%.dump"
robocopy "E:\rsnext_active" "H:\rsnext_backup\vol_active" /MIR /FFT /R:2 /W:3 /MT:8 /NP
🚑5. 緊急時 障害復旧マニュアル（専門知識不要・1分復旧）

⚡ ケースA：現役データ用 SSD（E: または D:）が突然故障した場合

  1. Windows スタートボタン右クリック ➔ ［ディスクの管理］ を開く。
  2. 故障した E:（存在しない場合はスキップ）のドライブ文字を削除する。
  3. 常時ミラー済みの G: ドライブを右クリック ➔ ［ドライブ文字とパスの変更］➔ E: に変更 する。
  4. これだけで（DB変更も設定変更も一切不要で）約1分で全画像の閲覧・新規着信がそのまま再開します。後日新しい4TB SSDを購入して空いた G: として挿すだけでミラー体制も復帰します。

🔄 ケースB：万一 PostgreSQL DB が破損・初期化された場合

  1. 第1手段（夜間ダンプ復元＋当日分自動補完）: H:\rsnext_backup\db_dumps\ の最新 .dump を pg_restore で戻し、当日着信分のみディスク走査スクリプトを実行。
  2. 第2手段（ダンプすら無い極限状態からの100%自己再構築）: 各検査フォルダ内の study_meta.json を全走査するリカバリスクリプトを実行するだけで、全検査履歴・患者ID・所見テキストまでDBへ自動復元されます。
